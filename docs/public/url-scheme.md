# `chorong://` links

Links let other tools (HTML reports, agent skills, chat messages) open a place in Chorong.
Code: `crates/cho-core/src/link.rs`. Build one with `cho link build`.

## Open a location

```
chorong://open?repo=github:acme/api&rev=3f9c1e2&path=src/http/webhook.rs&symbol=WebhookHandler::handle
```

| Parameter | Required | Meaning |
| --- | --- | --- |
| `repo` | yes | `github:OWNER/NAME`, `bitbucket:WORKSPACE/NAME`, `bitbucket-dc:HOST/PROJECT/NAME`, `local:~/path` (under the home directory) or `local:/absolute/path` |
| `pr` | no | **Provisional.** Pull request number: open the pull-request view ([below](#pull-request-links)) |
| `rev` | no | commit to open; default is the working tree or default branch. With `pr`, the pull request's head the link was made at. Must be a commit id or a valid git branch name (no leading `-`, spaces or `~^:?*[\`) |
| `base` | no | **Provisional.** The Before commit the link was made with: a full commit id (40 or 64 hex digits) |
| `side` | no | **Provisional.** `before` or `after` (default `after`): the version being read, and in Split which column gets focus |
| `path` | no | repository-relative file; no leading `/`, no `..`, no empty components |
| `symbol` | no | declaration to reveal, e.g. `Queue::push` |
| `line` | no | one-based line, used only when `symbol` is absent or doesn't resolve |
| `branch` | no | branch checked out when the link was made (informational; finds the worktree it was made from). Must be a valid git branch name |
| `dirty` | no | `1` if the working tree had uncommitted changes when the link was made |
| `from` | no | `graph` on links in a graph page, so the viewer can offer "Rebuild graph" (informational) |

Links that Chorong generates (graph pages, "copy link") always fill in `rev`, and `branch` and
`dirty` when they apply.

## Pull-request links

**Provisional:** `pr`, `base` and `side` may change or be removed if they cause problems.
Links without them behave as described elsewhere on this page.

```
chorong://open?repo=github:acme/api&pr=123&rev=89abcdef0123456789abcdef0123456789abcdef&base=0123456789abcdef0123456789abcdef01234567&side=before&path=src/http/webhook.rs&symbol=WebhookHandler::handle
```

Generated by **Copy chorong:// Link** in a pull-request view (a window on a cache worktree opened
for a pull request): the repository, path and declaration (or line) as for any link, plus `pr`,
`rev` (the head, a full commit id), `base` (the comparison's Before) and `side` (the version
the active pane shows). In a Before/After comparison with no pull request the link carries
`rev`, `base` and `side` only. A window that is neither a pull-request view nor comparing
makes links as before. Malformed values are refused when the link is parsed: a `pr` that is
not a positive number, a `base` that is not a full hex commit id, a `side` other than `before`
or `after`. `side` and `base` do nothing in a link without a comparison to put them in.

Opening one:

- With `pr`: if Chorong's cache has a worktree for that pull request, it opens (a window that
  already shows it comes forward). If not, **Chorong asks first**: "Open pull request #123 of
  github:acme/api?" with **Open** and **Cancel**, because a link from outside must not make
  Chorong fetch by itself. Open fetches the pull request into the cache (progress and Cancel in
  the status bar, as for **Open Remote…**); Cancel does nothing. When a worktree of your own for that repository is at the link's `rev`, the question adds **Open your worktree at this commit (~/path)**, which opens that folder with the same comparison, place and side and fetches nothing. A `pr` on a `local:` link is
  ignored.
- Then the comparison starts with Before = `base`, and the active pane goes to `side` at the
  link's path and declaration (its line when the declaration is not found). A window in Split
  on that file puts focus in the `side` column instead.
- A `base` that is not in the cache after the open (or, for a pull request already cached,
  not there without fetching) gives the notice "That Before commit isn't available." and the
  comparison starts with the merge base with the pull request's target instead.
- If the pull request has moved on (`rev` is not its current head), the commit-mismatch banner
  below applies. If `rev` is not in the cache at all, the banner says "That version of the
  pull request is gone" (after a fetch just made for the link) or that it is not in the cache
  (a pull request that was already cached), and the window shows the current head.
- Without `pr`, a link with `base` (and `rev`) opens the Before/After view at those commits in
  the worktree it resolves to, without any pull-request details. A link with neither opens as
  before.
- `cho link parse` prints `pr`, `base` and `side`; `cho open LINK` passes the link to the
  viewer as before; `cho open --view LINK` for a pull-request link opens that pull request
  (its `base` is the Before unless `--base` is given).

## Repository identity in generated links

Generated links name the **repository**, not the machine they were made on:

- If the worktree has a remote (`origin`, else the only remote), `repo` is that host's form:
  `github:OWNER/NAME`, `bitbucket:WORKSPACE/NAME` or `bitbucket-dc:HOST/PROJECT/NAME`. No
  flag is needed.
- Opening such a link resolves it to a local worktree of that repository: one Chorong has open
  or has opened before, matched by remote URL, preferring a worktree already at the link's
  `rev` or `branch`. With none, Chorong offers the web URL (and later, a fetch into its cache;
  never silently).
- With no remote, `repo` is `local:~/…` (home directory abbreviated), never the absolute
  path.
- An explicit `--repo` still overrides.

**Export for sharing** (`--share` in the CLI, a menu item in the viewer) is for pages and
links that leave the machine: it keeps `repo` and `rev`, and drops `branch`, `dirty` and the
worktree name from links and page headers. A remote such as `github:acme/api` still names
the organisation; that is the intended identity for sharing with colleagues.

As built (`crates/cho-git`, `app/src/links.rs`):

- Recognised remotes: `github.com` and `bitbucket.org` in any URL shape (HTTPS, SSH,
  scp-like), and Bitbucket Data Center as `https://HOST[/context]/scm/PROJECT/NAME.git` or
  SSH on port 7999. Any other host (GitLab, a self-hosted server Chorong can't identify, a
  file path) is not guessed at: the link uses `local:`.
- A worktree outside the home directory has no `~` form, so its `local:` link carries the
  absolute path; use `--repo` (CLI) to override. Decided: that is fine for your own links,
  but **Export for sharing refuses** a link that would contain an absolute path, and says to
  add a remote or pass `--repo`. That covers `cho graph --share`, the viewer's graph export with
  sharing on, and **Copy chorong:// Link for Sharing**. A `--repo local:~/…` name still passes, since
  it carries no absolute path; your own (non-sharing) links are unchanged.
- The viewer remembers folders it has opened (`recent.json` beside `trusted.json` in Chorong's
  settings) and resolves a remote link against them and their sibling worktrees
  (`git worktree list`). With none, it opens with a banner offering the web page.
- In the viewer, **Copy chorong:// Link** (Cmd-K C) copies a link to the declaration at the
  caret (its line when the name isn't unique in the file); **Copy chorong:// Link for Sharing**
  (command palette) drops the branch and dirty state. The path is relative to the
  repository's top level even when the viewer opened a subfolder.

Values are percent-encoded except `:` and `/`, which stay literal for readability.

## Open an investigation

```
chorong://investigation?src=https://example.com/trace.json
chorong://investigation?src=/home/me/traces/boot.json
```

`src` is an absolute path or an `https://` URL (no credentials in it); anything else is
refused. The viewer opens a local file in the window for its repository (the nearest git
worktree holding the file, else a worktree Chorong knows for the investigation's `repo`), asking
first if Chorong has never opened that folder, and hands the link to the running viewer like any
other link. Only the file itself is read: nothing it names is fetched or run. An `https://`
URL is fetched by the window it lands in (bounded: https only, a size limit and a timeout, no
credentials, redirects only to https), and the investigation opens there if it is about that
window's repository. See the user guide, "Tours and call stacks".

## OS registration (ships with the reference graph)

Clicking a `chorong://` link in a browser, such as a node in a graph page
([graph.md](graph.md)), must open Chorong.

- **macOS:** `chorong-app` is packaged as an `.app` bundle declaring the `cho` scheme
  (`CFBundleURLTypes` in `Info.plist`). macOS delivers the link to the running app, which
  handles it through GPUI's open-URL callback.
- **Linux:** a `.desktop` file with `MimeType=x-scheme-handler/chorong`, registered with
  `xdg-mime default`.
- **One running viewer.** A link goes to the viewer that already has the repository open,
  never a second copy. On macOS the OS does this. On Linux a newly launched `chorong-app`
  hands the link to the running instance over a per-user local socket and exits; if none is
  running, it opens normally.
- **The window comes forward** and the link is recorded in back/forward history like any
  other jump.
- **Unknown repository.** A `local:` path that isn't open is opened in a new window. A
  remote repository that isn't cached offers to fetch it; it is never fetched silently.

As built (`app/src/main.rs`, `app/src/instance.rs`, install steps in
[building.md](building.md#registering-chorong-for-chorong-links)):

- Linux: `app/linux/chorong.desktop` and `scripts/install-linux.sh`. The first viewer listens
  on a per-user socket (`$XDG_RUNTIME_DIR/chorong/viewer.sock`, else `/tmp/chorong-UID/`, folder
  mode 0700); a later `chorong-app chorong://…` or `chorong-app PATH` sends the link or the absolute
  path (one line, answered `ok`) and exits, so `cho PATH` reuses the running viewer too
  ([cli.md](cli.md#cho-path)).
- macOS: `app/macos/Info.plist` (`CFBundleURLTypes`) and `scripts/bundle-macos.sh`; links
  arrive through `Application::on_open_urls`. Not yet tested on a Mac.
- A link goes to the window whose folder is the link's worktree; it comes forward and the
  jump is recorded in history. Otherwise a new window opens. A remote repository with no
  known worktree shows the "not on this machine" banner (fetching is not built yet).

## Commit mismatch

A link records the commit it was made at, but the checkout may have moved since (switched
branch, pulled, rebased) by the time it is clicked. Chorong opens **the current checkout by
default** and makes the difference visible, because that is the code you are working on
and what your editor shows.

1. **The declaration still exists at the current commit.** Anchors name a file and a
   declaration, not a line, so this is the usual case. Chorong reveals it and shows a banner:
   "Link made at `3f9c1e2` on `feature/sessions`; this checkout is at `a71d004` on `main`".
   The banner offers:
   - **View at `3f9c1e2`:** the file as it was, read from the git object store, read-only.
     The checkout is never touched. Semantic features use that commit's cached index if
     there is one; otherwise the view is syntax-only and says so. The current index is never
     applied to other code.
   - **Open worktree:** if another worktree of the same repository has `3f9c1e2` (or the
     link's `branch`) checked out, open the link there instead (found with `git worktree
     list`). Opening a worktree is just opening a folder.
   - **Rebuild graph** (when the link came from a graph page): a fresh page from the
     current commit.
2. **The declaration is gone** (renamed, moved or deleted). Chorong says so ("`createSession`
   not found at `a71d004`") and offers the same choices. It never falls back to a
   similar name.
3. **Same commit, but the link or the checkout has uncommitted changes:** a smaller note,
   "link made before (or with) local edits", and the current file opens.

Chorong never switches the checkout itself (no `git checkout` or `git switch`): it is
read-only. "Switching back" means opening the other worktree, or the old commit read-only.
The banner shows the `git switch` command to copy, for anyone who wants to move the
checkout themselves.

As built (`app/src/view/mismatch.rs`):

- The banner appears when the link has a `rev` and this checkout's `HEAD` is another commit.
  A link whose symbol is gone at the checkout's commit is not moved to its `line` either:
  the line belongs to the other commit. At the same commit, `line` is used as documented.
- **View at** reads the file with `gix` from the object store and shows it read-only, with
  `@ rev (from git)` in its header and "At rev, read from git · syntax only" in the status
  bar. The index is used only when the cached index was built at exactly that commit on a
  clean tree. **Back to the checkout** returns to the current file.
- **Open worktree** lists `git worktree list` entries at the link's commit (or on its
  branch) and opens the link there, in that worktree's window or a new one.
- **Copy git switch command** copies `git switch BRANCH` (or `git switch --detach REV`).
- If the commit is not in the repository at all, the banner says so (fetch it to view it).

## Status

Parsing and building are implemented. `chorong-app` accepts `chorong://open` links on its command
line: `local:` links open their folder, and remote links open a worktree Chorong knows (see
above). `chorong://investigation` links open tours and call stacks in the viewer. Fetching a
remote repository into a cache is planned.
