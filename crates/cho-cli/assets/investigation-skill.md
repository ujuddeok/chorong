# Writing Chorong investigations

Chorong is a read-only code viewer. It renders **investigations**: JSON files of claims about
code, where every claim points at a real declaration. Chorong checks each claim against the
source and labels it `verified`, `claimed` or `broken`, so precision matters more than
coverage. This skill was generated by `cho {{CHORONG_VERSION}}` for investigation format
version {{FORMAT_VERSION}}: write `"chorong": {{FORMAT_VERSION}}`.

## Written and derived

Every part of an investigation is either **derived** (a fact Chorong works out from the code
and its index) or **written** (your claim, shown as claimed at best). Ask Chorong for the
mechanical facts instead of grepping for them or typing them in; write only the judgement.

| Ask Chorong (mechanical) | Write (judgement) |
| --- | --- |
| `cho outline PATH --json`, `cho find PATH SYMBOL --json`: exact declaration names | which steps matter, and their names |
| `cho symbols QUERY --json`: where a name is declared | the narrative: `summary`, `points`, notes |
| `cho references FILE LINE:COL --json`, `cho graph --symbol Q --in --json`: every use and caller (needs `cho index`) | what a use means, risk, decisions |
| `cho graph --diff BASE..HEAD --blast-radius --json`: what a change can reach | comparison results and callouts |
| `cho changes --merge-base TARGET --json`: what a branch changed | evidence and runtime values |

Never write line numbers, `file:line` lists, call depth, "called by" or diagram positions:
Chorong derives them, and they would go stale.

## Workflow

1. **Pin the revision.** Record the exact commit you read: `git rev-parse HEAD`. Every anchor
   refers to that commit.
2. **Get the facts from Chorong** (table above), then **read the real code**. Follow concrete
   call sites from the entry point the question asks about to the boundary it asks about.
   Never bridge a gap with a guessed callee.
3. **Name declarations exactly.** Confirm each anchor with `cho find PATH SYMBOL --json`.
   `unique` means it will resolve. For `ambiguous`, qualify it further (`Type::method`,
   `Class.method`) or add an `excerpt`.
4. **Write the file** into the repository being read, as
   `.chorong/investigations/SHORT-NAME.json`.
5. **Check it:** `cho investigation check FILE --root REPO --json`. Fix every `broken`
   anchor and every entry in `messages` before handing it over. Exit code 0 means every
   anchor resolved.

## Choosing the kind

- `callstack`: trace **one path** through the code, outermost call first.
- `tour`: read code **in order**. This includes "look at these files together to learn how
  a feature works, with these chunks highlighted": a tour (one step is fine) whose view
  shows several editor panes with highlights. A tour step can hold a `callstack` pane.
- `comparison`: **two or more paths that do the same job** (a REST handler and a SOAP
  handler, two queue backends). Sides, rows aligned by job, variants.
- `diagram`: an **unordered picture** of how parts relate.
- `pr-overlay`: notes on a pull request; needs `"pr": {"number", "base", "head"}` with
  `head` equal to `rev`.

## A call stack

```json
{
  "chorong": {{FORMAT_VERSION}},
  "title": "How a placed order reaches the confirmation email",
  "kind": "callstack",
  "repo": "github:OWNER/NAME",
  "rev": "3f9c1e2a7b4d",
  "summary": "An order is validated, stored, then queued; a worker sends the email later, so a mail failure never fails the request.",
  "points": [
    "The request returns once the job is queued.",
    "Mail delivery is handed to a vendor and only logged on failure."
  ],
  "generator": "your-agent-or-skill-name",
  "nodes": [
    { "id": "place", "name": "Validate and store", "evidence": "read",
      "anchor": { "path": "src/orders/service.rs", "symbol": "OrderService::place", "from": "validate(", "to": "insert(&order)?;" },
      "note": "Stores the order before queueing, so a queue failure leaves a stored, unconfirmed order." },
    { "id": "insert", "name": "Insert the row",
      "anchor": { "path": "src/orders/store.rs", "symbol": "insert", "excerpt": "DB.execute(" } },
    { "id": "push", "name": "Queue the email",
      "anchor": { "path": "src/jobs/queue.rs", "symbol": "Queue::push" } },
    { "id": "run", "name": "Worker loop",
      "anchor": { "path": "src/jobs/worker.rs", "symbol": "Worker::run" } },
    { "id": "send", "name": "Send the email", "evidence": "inferred",
      "anchor": { "path": "src/mail/mailer.rs", "symbol": "send_confirmation", "excerpt": "MAIL_VENDOR.send(message)" },
      "values": ["template = \"order-confirmed\""],
      "note": "Assumed to be the only job kind; other producers were not searched." }
  ],
  "externals": [
    { "id": "db", "what": "database", "label": "Orders database", "evidence": "read" },
    { "id": "vendor", "what": "vendor", "label": "Mail delivery service", "evidence": "inferred" }
  ],
  "edges": [
    { "from": "place", "to": "insert", "rel": "calls" },
    { "from": "insert", "to": "db", "rel": "data-flow", "note": "One INSERT per order." },
    { "from": "place", "to": "push", "rel": "calls" },
    { "from": "push", "to": "run", "rel": "data-flow", "note": "Through the channel, on the worker thread." },
    { "from": "run", "to": "send", "rel": "dispatches", "note": "Matched on the job kind in `Worker::handle`." },
    { "from": "send", "to": "vendor", "rel": "calls" }
  ],
  "groups": [
    { "label": "Per request", "members": ["place", "insert", "db", "push"] },
    { "label": "On the worker", "members": ["run", "send", "vendor"] }
  ],
  "steps": ["place", "insert", "db", "push", "run", "send", "vendor"],
  "untraced": [
    { "what": "What the vendor does with a rejected message", "at": "send", "why": "Outside the repository." }
  ]
}
```

- `repo`: `github:OWNER/NAME`, `bitbucket:WORKSPACE/NAME`, `bitbucket-dc:HOST/PROJECT/NAME`,
  or `local:/absolute/path`. `rev`: the full hash from step 1.
- `steps` (required for `callstack` and `tour`) is the reading order. `edges`, `groups`,
  `externals`, `points` and `untraced` are optional.
- **Step names** (`name`) are short: three to five words saying what the step does. Put the
  explanation in `note`.
- **Summary points** (`points`) are the answer in a few bullets, including any assumption it
  depends on; `summary` is a sentence or two for whoever reads the file.
- **Phases:** give a group `"phase": "setup"` for what runs once (start-up, registration,
  configuration) and `"phase": "call"` for what runs on each request. Setup steps are
  numbered S1, S2… (see the tour under "Branches and variants").
- **Untraced:** list what you couldn't follow (`what`, `why`, and optionally `at`: the code node
  or anchor where you stopped) instead of guessing past it.
- Unknown fields are rejected. Run `cho schema investigation` for the full JSON Schema.

## Writing the text

Chorong shows text as you write it; very little is formatted.

- A step's `note`, an action step's `note` and an external node's `note` are **inert
  Markdown**: only `` `code` `` spans, `[text](target)` links, `**bold**` and `*italic*` are
  formatted. A line starting with `- `, `1. ` or `#` starts a new line, but is not drawn as a
  list or heading. Tables, images and HTML show as the characters you typed, so don't use
  them. Use emphasis sparingly. A link shows its real target; only `https://` and `chorong://`
  links open.
- `points`, `untraced`, comparison `callout`s and a highlight's `name` and `note` are **plain
  text**: backticks show as backticks.
- A step's `note` is shown above the code and wraps: the explanation goes there.
- A highlight's `name` is its **label**, on a one-line strip above its chunk: two to five
  words. Its `note` is **commentary**, a sentence or two shown under the label in the step's
  list of chunks. A chunk that needs more than that is a point of its own: make it a step.
- `points` are what the reader sees as the answer ("Summary · 3 points"). `summary` is not
  shown in the viewer: don't rely on it to tell the reader anything the points don't.

## Anchors

- `path`: repository-relative, with no leading `/` and no `..`.
- `symbol`: the declaration's own name, qualified as the language writes it. Rust uses
  `Type::method` and `module::function`; Python, TypeScript, JavaScript, Swift and Java use
  `Class.method` (Java nested types: `Outer.Inner.method`; a constructor is named after its
  class, `Queue.Queue`). Leave it out only to point at a whole file.
- `excerpt`: a short, exact substring inside that declaration, to point at one call.
- `from` / `to`: a range by text, from the start of `from` to the end of `to` (searched
  after `from`). Use it instead of a long `excerpt`. Use `excerpt` or `from`/`to`, not both.
- If the code changes and the text is gone, Chorong marks the anchor broken rather than
  pointing somewhere wrong. **Never write line numbers.**

### Choosing how to point

What the reader sees: a step's declaration is tinted faintly, and an `excerpt` or
`from`/`to` inside it is tinted darker.

- **The declaration alone** (`symbol`) by default: the stop is the whole function or type.
- **Add an `excerpt` or `from`/`to`** only when one line or a few lines carry the point in a
  longer declaration (the call that hands the job on, the check that rejects the request).
  Not on a short declaration: the faint tint already shows it.
- **Highlights** (a view's editor pane, below) only when one step needs several places read
  together. Each is numbered, has a label (`name`), optional commentary (`note`), and can
  have its own excerpt. With highlights the step's anchor is not tinted: it names the step
  (its place in the list, the graph and its label). If the reader should read the anchor too,
  list it as a highlight by its node id (`"anchor": "handle"`).
- One point per step: several points read in order are several steps, not highlights. Steps
  can share a file.

## External nodes

When the path leaves the code for something that isn't code, add an entry to `externals`
instead of faking an anchor: `what` is `model`, `database`, `service`, `vendor`,
`platform`, `limit` (a platform or quota limit) or `other`. Externals share node ids, so
steps, edges, groups and comparison rows can name them. Chorong always reports them as
`not-in-code`.

## Evidence and runtime values

- `evidence`: `read` (you read the code that does it) or `inferred` (you concluded it
  without reading it). Say what you didn't check in `note`.
- `values`: runtime values as you understood them (`strictness = Lenient`, `cache hit`,
  `not reached`).

Both are always shown as **your claims**, beside Chorong's own label, and never verified. Write
them as claims, not as facts Chorong checked.

## Relations

Use the most specific relation that you saw in the source:

- `calls`: a direct call that you read at a call site in `from`.
- `dispatches`: an indirect call, through a callback, trait object, interface, route table,
  event bus or registration. Say how in `note`.
- `references`: `from` mentions `to` without calling it.
- `implements`: `from` implements or overrides `to`.
- `data-flow`: a value produced in `from` reaches `to`.
- `contains`: module, type or file containment.
- `related`: anything else. Explain it in `note`.

## Views

A `tour` or `callstack` step can say **what** its page shows, never **where**: `views` maps
a step id to `panes` and an `arrangement`. Chorong lays it out. Never write sizes, coordinates
or positions. A step with no view shows its anchor in an editor.

- Panes: `editor` (an `anchor`, or `highlights`: several chunks of **one file**, each with a
  `name` and an optional `note`), `context` (an `anchor`, pinned), `outline` (a `path`), `graph` (`of` a node
  or anchor, `direction` `in`, `out` or `both`, `depth` 1 to 5), `callstack` (this
  investigation), `file-tree` (an optional `path`), `diff` (below).
- Arrangements: `single`, `side-by-side`, `stacked`, `main-side`, `grid`.
- Anchors in panes are a node id or an anchor written in place.
- A highlight's `name` is a few words ("Token checked first"); its `note` adds a sentence or
  two; the step's `note` explains how they fit together. Highlights are numbered in the order
  you list them, which is the reading order of the step's list: list them in the order to
  read them.

This tour is "read these files together to learn how requests are filtered", in one step:

```json
{
  "chorong": {{FORMAT_VERSION}},
  "title": "How the request pipeline filters requests before routing",
  "kind": "tour",
  "repo": "github:OWNER/NAME",
  "rev": "3f9c1e2a7b4d",
  "summary": "Every request passes authentication, then a body-size limit, then the router. Each filter answers on its own and stops the request.",
  "nodes": [
    { "id": "pipeline", "name": "The request pipeline", "evidence": "read",
      "anchor": { "path": "src/http/pipeline.rs", "symbol": "handle" },
      "note": "Read the three files side by side: the pipeline, its two filters, and the router it ends in." }
  ],
  "steps": ["pipeline"],
  "views": {
    "pipeline": {
      "arrangement": "grid",
      "panes": [
        { "kind": "editor", "highlights": [
          { "anchor": { "path": "src/http/pipeline.rs", "symbol": "handle", "from": "match authenticate(req)", "to": "};" }, "name": "Auth first", "note": "A request without a valid token stops here with 401." },
          { "anchor": { "path": "src/http/pipeline.rs", "symbol": "handle", "excerpt": "router.dispatch(req)" }, "name": "Then route" } ] },
        { "kind": "editor", "highlights": [
          { "anchor": { "path": "src/http/pipeline.rs", "symbol": "authenticate", "excerpt": "verify_token(token)?" }, "name": "Token check" },
          { "anchor": { "path": "src/http/pipeline.rs", "symbol": "limit_body", "excerpt": "req.body.len() > MAX_BODY" }, "name": "Size limit" } ] },
        { "kind": "editor", "anchor": { "path": "src/http/router.rs", "symbol": "Router::dispatch" } },
        { "kind": "outline", "path": "src/http/router.rs" }
      ]
    }
  }
}
```

## Action steps and diffs

A tour can mix code with **what changed** and **what to do**.

- `actions`: steps that are instructions, not code. Each has an `id` (shared with node ids),
  a short `name`, a `note` saying what to do and why, and optional `commands`, each a `text`
  with an optional `label`. Chorong **never runs** a command: it shows it with a Copy button.
  Name actions in `steps` (and groups or views); never in `edges`, graph panes or anchors.
  Only `tour` files have actions.
- A `diff` pane shows one file between two revisions: `path`, `base` (a branch, tag or
  commit) and optional `head` (absent means the working tree). Get the revisions from
  `cho changes`; check reports one that doesn't resolve.
- An action's view can add panes beside its card ("run this, then watch this code"): give
  each editor an `anchor`, since the action has no code of its own.

This tour shows a change, asks the reader to run the migration, then opens the code:

```json
{
  "chorong": {{FORMAT_VERSION}},
  "title": "Saving orders after the schema change",
  "kind": "tour",
  "repo": "github:OWNER/NAME",
  "rev": "3f9c1e2a7b4d",
  "generator": "your-agent-or-skill-name",
  "nodes": [
    { "id": "insert", "name": "What changed in the insert",
      "anchor": { "path": "src/orders/store.rs", "symbol": "insert" } },
    { "id": "place", "name": "Who calls it",
      "anchor": { "path": "src/orders/service.rs", "symbol": "OrderService::place", "excerpt": "insert(&order)?" },
      "note": "Every placed order goes through the changed insert." }
  ],
  "actions": [
    { "id": "migrate", "name": "Run the migration",
      "note": "Apply the migration to your local database, then place an order to see the new column filled.",
      "commands": [
        { "label": "Apply", "text": "cargo run -p db -- migrate up" },
        { "label": "Check", "text": "psql -c 'select * from orders limit 1'" } ] }
  ],
  "edges": [ { "from": "place", "to": "insert", "rel": "calls" } ],
  "steps": ["insert", "migrate", "place"],
  "views": {
    "insert": { "panes": [ { "kind": "diff", "path": "src/orders/store.rs", "base": "main" } ] },
    "migrate": { "arrangement": "side-by-side",
                 "panes": [ { "kind": "editor", "anchor": "insert" } ] }
  }
}
```

## Branches and variants

Write mutually exclusive paths as **branches**, never as one sequence. In a tour or call
stack, top-level `variants` are branches: each overrides steps by id, with another `step`
or `missing` (shown as not reached).

```json
{
  "chorong": {{FORMAT_VERSION}},
  "title": "Reading the order request, and where a bad body stops it",
  "kind": "tour",
  "repo": "github:OWNER/NAME",
  "rev": "3f9c1e2a7b4d",
  "generator": "your-agent-or-skill-name",
  "nodes": [
    { "id": "routes", "name": "Register the routes", "anchor": { "path": "src/http/router.rs", "symbol": "routes" } },
    { "id": "create", "name": "Parse the order", "anchor": { "path": "src/http/orders.rs", "symbol": "OrderHandler::create", "excerpt": "parse_order(&req.body)" } },
    { "id": "place", "name": "Place the order", "anchor": { "path": "src/orders/service.rs", "symbol": "OrderService::place" } },
    { "id": "reject", "name": "Answer 400", "anchor": { "path": "src/http/orders.rs", "symbol": "OrderHandler::create", "excerpt": "Response::bad_request(e)" } }
  ],
  "edges": [
    { "from": "routes", "to": "create", "rel": "dispatches", "note": "Registered for `POST /orders`." },
    { "from": "create", "to": "place", "rel": "calls" }
  ],
  "groups": [
    { "label": "At start-up", "members": ["routes"], "phase": "setup" },
    { "label": "Per request", "members": ["create", "place"], "phase": "call" }
  ],
  "steps": ["routes", "create", "place"],
  "variants": [
    { "id": "bad-body", "label": "The body doesn't parse",
      "rows": { "create": { "step": "reject", "values": ["parse error"] },
                "place": { "missing": "not reached: the handler answers 400 first" } } }
  ]
}
```

## Comparisons

`"kind": "comparison"` lines up two or more paths that do the same job.

- `sides`: each an `id`, a `label` and a `path` of node ids, in order.
- `rows`: one per job, in path order, with a short `name`, a `phase`, and one cell per side:
  a `step` (with optional `values` and `note`) or a `missing` reason. **`missing` needs a
  reason.**
- `result`: `same`, `differs` or `missing`. When every side runs the same declaration, Chorong
  reports `same_code`, but two sides often run the same function with different values:
  then write `differs` and put the values in the cells. Chorong never overrides a written
  `differs`. A side with no step is always `missing`.
- `callout`: a few words on the row that matters ("Paths split here").
- `variants` on a side: another version of that side (a bulk endpoint, another backend),
  overriding only the rows it names. Variants are branches, not extra rows.

```json
{
  "chorong": {{FORMAT_VERSION}},
  "title": "Placing an order: REST handler and SOAP handler",
  "kind": "comparison",
  "repo": "github:OWNER/NAME",
  "rev": "3f9c1e2a7b4d",
  "summary": "Both handlers end in the same service call, but SOAP validates leniently, so it accepts orders REST refuses.",
  "points": ["Same service, different strictness.", "SOAP routing lives outside the code."],
  "nodes": [
    { "id": "rest-route", "name": "Register the route", "anchor": { "path": "src/http/router.rs", "symbol": "routes", "excerpt": "router.post(\"/orders\", OrderHandler::create)" } },
    { "id": "rest-parse", "name": "Parse JSON", "anchor": { "path": "src/http/orders.rs", "symbol": "OrderHandler::create", "excerpt": "parse_order(&req.body)" } },
    { "id": "rest-place", "name": "Place, strict", "anchor": { "path": "src/http/orders.rs", "symbol": "OrderHandler::create", "excerpt": "OrderService::place(order, Strictness::Strict)" } },
    { "id": "bulk-parse", "name": "Parse a JSON list", "anchor": { "path": "src/http/orders.rs", "symbol": "OrderHandler::create_bulk", "excerpt": "parse_orders(&req.body)" } },
    { "id": "soap-parse", "name": "Read the envelope", "anchor": { "path": "src/soap/endpoint.rs", "symbol": "from_envelope" } },
    { "id": "soap-place", "name": "Place, lenient", "anchor": { "path": "src/soap/endpoint.rs", "symbol": "SoapEndpoint::place_order", "excerpt": "OrderService::place(order, Strictness::Lenient)" } },
    { "id": "validate", "name": "Validate", "anchor": { "path": "src/orders/service.rs", "symbol": "validate" } }
  ],
  "sides": [
    { "id": "rest", "label": "REST handler", "path": ["rest-route", "rest-parse", "rest-place", "validate"],
      "variants": [ { "id": "bulk", "label": "Bulk endpoint", "rows": { "parse": { "step": "bulk-parse" } } } ] },
    { "id": "soap", "label": "SOAP handler", "path": ["soap-parse", "soap-place", "validate"] }
  ],
  "rows": [
    { "id": "route", "name": "Register the endpoint", "phase": "setup",
      "cells": { "rest": { "step": "rest-route" }, "soap": { "missing": "Mapped in the deployment descriptor, not in code." } } },
    { "id": "parse", "name": "Read the order", "phase": "call",
      "cells": { "rest": { "step": "rest-parse" }, "soap": { "step": "soap-parse" } }, "result": "differs" },
    { "id": "place", "name": "Call the service", "phase": "call",
      "cells": { "rest": { "step": "rest-place", "values": ["strictness = Strict"] },
                 "soap": { "step": "soap-place", "values": ["strictness = Lenient"] } }, "result": "differs" },
    { "id": "validate", "name": "Validate", "phase": "call",
      "cells": { "rest": { "step": "validate", "values": ["customer required"] },
                 "soap": { "step": "validate", "values": ["customer optional"] } },
      "result": "differs", "callout": "Paths split here" }
  ]
}
```

## A diagram

```json
{
  "chorong": {{FORMAT_VERSION}},
  "title": "What the job queue connects",
  "kind": "diagram",
  "repo": "github:OWNER/NAME",
  "rev": "3f9c1e2a7b4d",
  "nodes": [
    { "id": "queue", "anchor": { "path": "src/jobs/queue.rs", "symbol": "Queue" } },

    { "from": "service", "to": "queue", "rel": "references", "note": "Producer." },
    { "from": "worker", "to": "queue", "rel": "references", "note": "Only consumer found." },
```

## Honesty rules

- Never invent a declaration, and never point an anchor at a comment or a string.
- Write branches as branches (`variants`, or "If strict…", "On failure…" in a note). Don't
  present mutually exclusive paths as if they run one after another.
- When the code leaves the repository (a dependency, generated code, FFI), stop at the last
  call site you verified, add an external node or an `untraced` entry, and say in its `note`
  where control goes next.
- Put uncertainty in `note`, `evidence` and `untraced`, not in the structure. A `dispatches`
  edge with an honest note is better than a `calls` edge you didn't see.
- `evidence`, `values` and results are your claims. Never word them as if Chorong checked them.
